## 結論から

水平思考クイズ（いわゆる「ウミガメのスープ」）を Web で作りました。プレイヤーが**自由文で質問**し、出題者は **YES / NO / 関係ない / どちらとも言えない** の4つだけを返す、あの形式です。

自由文を受け取る以上、最初は「LLM に投げるしかない」と思っていました。実際に作ってみると逆で、**LLM は最後の保険に降格させたほうが、ゲームとしてまともに動く**というのが結論でした。

要点は4つです。

- 判定は **normalize → ルール表 → （未ヒット時のみ）LLM** の3層にする
- 日本語の表記ゆれは **NFKC + カタカナ→ひらがな + 記号除去**でほぼ潰せる
- 正解判定は「**グループ間 AND × グループ内 OR**」の2階建てにすると、部分点フィードバックがタダで手に入る
- LLM は既定 OFF・BYOK。**LLM なしで完結する**ことをベースラインにする

そして副産物として、エンジニア編の問題が**バグ調査の型カタログ**になりました。「本番だけ画像が出ない」「金曜だけデプロイが落ちる」「調べると消えるバグ」あたりは、実務で一度は踏むやつです。実際に遊べるものは [ディレクターが作ったウミガメのスープ](https://codequest.work/games/lateral-thinking/?utm_source=zenn&utm_medium=article&utm_campaign=lateral-thinking-quiz-yes-no-engine) に置いてあります（登録不要・ブラウザ完結）。

この記事は、その判定エンジンの設計メモです。

## なぜ「LLM に全部投げる」をやめたのか

素直に考えると、こうしたくなります。

```
プレイヤーの質問 + 真相 → LLM → YES / NO
```

これは動きます。動きますが、クイズとしては壊れます。理由は4つあって、**決定的なのは2つ目**です。

| 懸念 | 内容 |
| --- | --- |
| コスト | 1問あたり質問は10〜30回。問題数を掛けると馬鹿にならない |
| **一貫性** | **同じ質問に別の判定を返した瞬間、推理ゲームとして破綻する** |
| APIキー | サーバーを持たない静的サイトなので、キーの置き場所がない |
| レイテンシ | 「YES」の1語を出すのに毎回1秒待たされるとテンポが死ぬ |

推理ゲームの本質は「積み上げた情報が矛盾しないこと」です。5回前に「キャッシュは関係ない」と言われたのに、言い方を変えて聞いたら「YES」が返ってくる。これはバグではなく**ゲームの破綻**です。

つまりここで欲しいのは、賢さではなく**決定性**でした。決定性が欲しいなら、素直に決定的なものを書けばいい。それがルール表です。

## 全体の流れ

```js
// 1. ルール表で判定する（決定的・即時・無料）
const ruleResult = judgeByRules(question, puzzle)
if (ruleResult) return showVerdict(ruleResult.verdict, ruleResult.note)

// 2. ルール表が外した & AI が有効なときだけ LLM に回す
if (aiStatus() !== "on") {
  return showVerdict("UNKNOWN", "別の言い方で聞いてみてください")
}

const text = await callAI({ provider, prompt: buildAiPrompt(question, puzzle), apiKey })
const verdict = parseAiVerdict(text)
return showVerdict(verdict ?? "UNKNOWN", "", "ai")
```

AI が OFF でも、ゲームは最後まで遊べます。**OFF が既定値**で、ON にするのはプレイヤーが自分の API キーを入れたときだけです。

## 1. 日本語の表記ゆれを正規化する

自由文で来るので、「キャッシュ」「きゃっしゅ」「ｷｬｯｼｭ」「キャッシュ？」が全部同じものとして扱われないと、ルール表を何百行書いても穴だらけになります。

```js
export function normalize(text) {
  if (typeof text !== "string") return ""
  return text
    .normalize("NFKC")                                            // 全角英数・半角カナを統一
    .toLowerCase()                                                // 大文字小文字を統一
    .replace(/[ァ-ヶ]/g, (ch) =>                                   // カタカナ → ひらがな
      String.fromCharCode(ch.charCodeAt(0) - 0x60))
    .replace(/[\s　]/g, "")                                        // 空白（半角・全角）を除去
    .replace(/[、。，．,.!?！？「」『』【】（）()［］\[\]・:;：；'"`]/g, "") // 記号を除去
}
```

```js
normalize("大文字・小文字 は 関係アル？")
// → "大文字小文字は関係ある"
```

4つの処理には、それぞれ別の役割があります。

**NFKC** は Unicode の互換正規化です。全角の `ＣＳＳ` → `CSS`、半角カナの `ｷｬｯｼｭ` → `キャッシュ` がここで揃います。日本語入力の事故をまとめて吸収してくれるので、まずこれを通します。

**カタカナ→ひらがな**は `charCodeAt() - 0x60` でやっています。Unicode 上でひらがな（U+3041〜）とカタカナ（U+30A1〜）は 0x60 ちょうどずれて並んでいるので、引き算だけで変換できます。これがあると、ルール表には「きゃっしゅ」と「キャッシュ」のどちらか片方を書けば済みます。

:::message
`[ァ-ヶ]` の範囲なので、長音符 `ー` は変換されません（ひらがな側にも同じ `ー` を使うため、変換不要）。逆に `ヴ` は `ゔ` になります。
:::

**空白と記号の除去**は、マッチを「含むかどうか」だけの判定に単純化するためです。「大文字・小文字」と「大文字小文字」がズレるのを防ぎます。

ポイントは、**ルール表側の語も同じ `normalize()` に通す**ことです。片側だけ正規化しても意味がありません。

```js
function ruleMatches(rule, normalizedQuestion) {
  if (rule.not?.some((w) => normalizedQuestion.includes(normalize(w)))) return false
  return Boolean(rule.any?.some((w) => normalizedQuestion.includes(normalize(w))))
}
```

## 2. ルール表：`any` / `not` と「上から順」

1問ぶんのルールは、こういう配列です。

```js
{
  id: "e-case-sensitive",
  title: "本番だけ画像が出ない",
  puzzle: "ローカルでもステージングでも表示される画像が、本番だけ表示されない。ファイルは確かにアップロードされている。",
  truth: "ファイル名は Logo.png だったが、コードからは logo.png で参照していた。開発者の macOS はファイル名の大文字小文字を区別しないため誰も気づかず、本番の Linux サーバーは区別するため 404 になっていた。",
  rules: [
    { any: ["大文字", "小文字", "case sensitive", "ケース"], a: "YES", note: "そこが核心です" },
    { any: ["ファイル名", "命名", "つづり", "スペルミス", "タイプミス"], a: "YES" },
    { any: ["os", "windows", "mac", "linux", "ファイルシステム"], a: "YES" },
    { any: ["存在", "アップロード", "上げ忘れ", "デプロイ漏れ"], a: "NO", note: "ファイルは確かにあります" },
    { any: ["権限", "パーミッション", "chmod", "403"], a: "NO" },
    { any: ["キャッシュ", "cache"], a: "NO" },
    { any: ["文字コード", "エンコード", "utf", "全角", "絵文字"], a: "NO" },
    { any: ["時間", "時刻", "タイミング", "曜日"], a: "IRRELEVANT" },
  ],
}
```

判定は**上から順に見て、最初にマッチしたものを採用**します。

```js
export function judgeByRules(question, puzzle) {
  const normalized = normalize(question)
  if (!normalized) return null

  for (const rule of puzzle.rules ?? []) {
    if (ruleMatches(rule, normalized)) {
      return { verdict: rule.a, note: rule.note, source: "rules" }
    }
  }
  return null // 未ヒット。呼び出し側が LLM フォールバックを判断する
}
```

順序が意味を持つので、**具体的な条件ほど先に置く**のが運用ルールです。「ファイル名の大文字小文字ですか？」は上から2つとも刺さりますが、先に書いてある「大文字・小文字」の行が勝ち、`note` として「そこが核心です」まで返せます。

`not` は除外条件です。広い語で拾いたいが特定の文脈だけ外したい、というときに使います。

```js
// 「キャッシュ」は NO。ただし「ブラウザキャッシュ」の話だけは別ルールに任せたい
{ any: ["キャッシュ"], not: ["ブラウザ"], a: "NO" }
```

### `IRRELEVANT` という第3の返答が効く

YES / NO しかないと、プレイヤーは**総当たり**を始めます。「時間帯は関係ありますか？」に NO が返ると、「じゃあ曜日は？」「時刻は？」と潰し続けることになる。

そこに `IRRELEVANT`（関係ありません）があると、「その方向は丸ごと捨てていい」という情報になります。NO は1つの可能性を消すだけですが、IRRELEVANT は**探索の枝を丸ごと刈る**ので、情報量が桁違いに大きい。実際に遊んでもらうと、ここでテンポが変わります。

`UNCERTAIN`（どちらとも言えない）も用意していますが、これは「真相に情報がないので断定できない」ケース専用です。逃げ道として多用すると、プレイヤーは何も学べません。

## 3. 正解判定は「グループ間 AND × グループ内 OR」

「わかった！」と宣言したときの正誤判定です。ここが一番設計を悩みました。

素朴にやると、キーワードを1つでも含めば正解にしてしまいます。しかしこの問題で「大文字小文字が関係してますか？」だけでは、正解とは言えません。**「ファイル名の大文字小文字が食い違っていた」まで言えて初めて正解**です。

かといって完全一致は無理です。言い方が無数にあります。

そこで、**概念ごとにグループを作り、グループ内は OR、グループ間は AND** にしました。

```js
solutionKeys: [
  ["大文字", "小文字", "case", "ケース", "けーす"],           // 概念A: 大小の区別
  ["ファイル名", "名前", "命名", "パス", "つづり", "綴り"],    // 概念B: 何の大小か
],
```

```js
export function checkSolution(answer, puzzle) {
  const normalized = normalize(answer)
  const groups = puzzle.solutionKeys ?? []
  const matched = groups.filter((group) =>
    group.some((word) => normalized.includes(normalize(word)))
  ).length

  return { correct: groups.length > 0 && matched === groups.length, matched, total: groups.length }
}
```

「概念Aと概念Bの両方に触れているか。ただし各概念の言い方は問わない」という判定になります。

そしてこの構造の**うれしい副産物**が `matched / total` です。全部は揃っていないが一部は当たっている、という状態が数値で取れるので、部分点フィードバックが追加コストゼロで出せます。

```js
if (matched > 0) {
  print(`惜しい。核心の ${matched}/${total} までは合っています。もう少し具体的に。`)
} else {
  print("違います。質問を続けてください。")
}
```

「違います」しか返ってこないゲームは、そこで離脱されます。「惜しい、1/2 までは合ってる」が出るだけで、もう一度考えてもらえる。**判定ロジックの副産物が、そのまま UX になった**部分です。

## 4. LLM は「フォールバック」に降格させる

ここまでで、ルール表が外したときだけ LLM に回る状態になっています。この設計だと、LLM に求めることが激減します。**自由に推論してほしいのではなく、既存の判定と矛盾しない1語を返してほしいだけ**です。

そこでプロンプトには、真相に加えて**既存のルール表そのもの**を根拠として渡しています。

```js
export function buildAiPrompt(question, puzzle) {
  const knownRules = (puzzle.rules ?? [])
    .slice(0, 40)
    .map((rule) => `- 「${rule.any.join(" / ")}」に関する質問 → ${rule.a}`)
    .join("\n")

  return [
    "あなたは水平思考クイズの出題者です。以下の真相に照らして、プレイヤーの質問に判定だけを返してください。",
    "",
    "【真相（プレイヤーには非公開）】", puzzle.truth, "",
    "【既存の判定基準（一貫性を保つため必ず従うこと）】", knownRules, "",
    "【プレイヤーの質問】", question, "",
    "【出力ルール】",
    "- YES / NO / IRRELEVANT / UNCERTAIN のいずれか1語だけを出力する",
    "- 真相から論理的に導けるなら YES または NO",
    "- 真相と無関係な事柄への質問は IRRELEVANT",
    "- 真相に情報がなく断定できない場合のみ UNCERTAIN",
    "- 説明・理由・補足は一切書かない。真相を漏らさない",
  ].join("\n")
}
```

**ルール表を一緒に渡しているのが肝**です。これがないと、LLM は「ルール表なら NO を返す質問」に YES を返してしまい、プレイヤーから見ると出題者が前言撤回したように見えます。ルール表は仕様書として渡す価値があります。

受け取り側は、1語だけ抜き出します。

```js
export function parseAiVerdict(text) {
  const upper = (text ?? "").toUpperCase()
  if (upper.includes("IRRELEVANT")) return "IRRELEVANT"
  if (upper.includes("UNCERTAIN")) return "UNCERTAIN"
  if (/\bYES\b/.test(upper)) return "YES"
  if (/\bNO\b/.test(upper)) return "NO"
  return null // 判別できなければ UNKNOWN 扱い（=「別の言い方で聞いてください」）
}
```

`YES` / `NO` に `\b`（単語境界）を付けているのは、`NOT` や `KNOWN` のような単語の一部を誤って拾わないためです。判別できなければ `null` を返し、UI 側は素直に「別の言い方で聞いてみてください」に落とします。**LLM の出力を信用しきらない**のは、フォールバックである以上ちょうどいい距離感でした。

:::message alert
**ブラウザから直接 API を叩くことについて**

このゲームはサーバーを持たない静的サイトなので、AI を使う場合はプレイヤー自身の API キーをブラウザに入れてもらう BYOK 方式です。Anthropic の API をブラウザから呼ぶには、明示的なオプトインヘッダが要ります。

```js
headers: {
  "x-api-key": apiKey,
  "anthropic-version": "2023-06-01",
  "anthropic-dangerous-direct-browser-access": "true",
}
```

ヘッダ名が `dangerous` から始まっているのは伊達ではなく、「危険性を理解した上で使え」という設計です。**成立するのは「キーの持ち主＝そのブラウザの利用者」という条件下だけ**で、自分のキーを配って他人に使わせるなら、この構成は取ってはいけません（キーが丸見えになります）。今回は AI が既定 OFF で、なくても完全に遊べるからこそ許容できる構成です。
:::

## 実際どれくらいルールを書いたか

現時点で **68問・約1,080ルール**（1問あたり平均16ルール）です。「LLM に頼らない」の代償はここに全部乗っています。

ただ、書いてみて気づいたのは、**この作業は実装ではなくコンテンツ制作だった**ということです。「この問題、プレイヤーは何を聞いてくるだろう？」を列挙する作業は、そのまま**問題の質を上げる作業**でした。想定質問が10個しか出てこない問題は、だいたい問題として面白くない。ルールを書きながら「この問題は誘導が足りない」と気づいて問題文を直す、という往復が何度も起きました。

LLM に投げていたら、この往復は発生しなかったと思います。

## エンジニア編がバグ調査の型カタログになった

余談ですが、エンジニア編（17問）は結果として実務のパターン集になりました。真相だけ並べるとこんな感じです。

- **本番だけ画像が出ない** → macOS は大小同一・Linux は別物。参照が `logo.png`、実体が `Logo.png`
- **金曜だけデプロイが落ちる** → 週次バックアップ cron の DB ロックと、マイグレーションの競合
- **まとめて実行すると落ちるテスト** → 先行テストが共有状態を戻していない。犯人は落ちたテストではなく実行順
- **直したのに直らない CSS** → Service Worker が古い CSS を配信。リロードより手前で応答するので突破できない
- **その社員だけ登録できない** → 姓が `Null`。文字列の Null が「値なし」として扱われた
- **月末だけ合わない請求額** → 金額を浮動小数で保持。1件では見つからず、合計で表面化する
- **調べると消えるバグ** → 競合状態。ログ出力が処理時間を伸ばし、すれ違いの窓を潰していた

「症状から原因を逆算する」というのは、水平思考クイズとまったく同じ構造をしています。ジャンルは通常編・エンジニア編・デザイナー編・動画編集者編の4つで、それぞれ17問ずつ、難易度は★〜★★★★です。

## まとめ

- 自由文入力だからといって、LLM が必須とは限らない
- 推理ゲームに必要なのは賢さより**決定性**。ルール表はその点で本質的に向いている
- 日本語の表記ゆれは **NFKC + カタカナ→ひらがな + 記号除去**でかなり潰せる。**両側を同じ関数に通す**のを忘れずに
- 正解判定を **AND × OR の2階建て**にすると、部分点フィードバックが無料で付いてくる
- LLM をフォールバックにすると、**プロンプトに既存ルールを渡して一貫性を縛る**という手が使えるようになる

「まず LLM なしで動くベースラインを作り、埋まらない隙間だけ LLM に渡す」——判定ロジックに限らず、しばらくはこの順番で作るのが安全だと感じています。
