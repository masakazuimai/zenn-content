## はじめに

Claude Code を「1人の助手」ではなく、**役割を分けた組織として毎日動かす**には、定期実行を足すだけでは足りませんでした。足りなかったのは、動いたあとの層です。結果を必ず報告させる、動かなかったものを見張る、結果を次の判断に使う、うっかりの操作を止める。この4つです。

この記事は、ひとりで Web 制作と自社ツールを運営している筆者が、2026年11月時点で実際に回している構成の記録です。数字はすべて手元の設定とログで数え直したものです。

1か月前、「16部署を作って14部署を解体した」という記事を書きました。

https://zenn.dev/orectic/articles/claude-code-ai-organization-dismantle

そこで決めたのは「ボトルネックが先、部署が後」という順番でした。この記事はその続きで、その順番どおりに足していった結果、いまどう回っているかを書きます。

## 全体像：人間1人、COO 1人、部署15、定期実行48本

| 層 | 中身 | 数（2026-11-13 時点） |
|---|---|---|
| 人間（CEO 役） | 公開・支払い・方針を決める。AI が聞くのは選択式だけ | 1 |
| COO（メインの Claude Code） | 頼みごとを受け、部署に振り、結果をまとめる | 1 |
| 部署（サブエージェント） | `.claude/agents/` に定義した専門の担当 | 15 |
| 定期実行 | macOS の launchd で決まった時刻に `claude -p` などを起動 | 読み込み中 48本（登録 60・止めているもの 12） |
| 運用の層 | 完了報告メール・見張り役・学びの台帳・守りのフック | 下で説明 |

上の4行は、検索すれば作り方がたくさん出てきます。この記事で書きたいのは5行目です。

## 1. 定期実行は、結果を必ずメールで返す

定期実行を増やして最初に困ったのは、**動いたかどうかが分からない**ことでした。Claude がエラーで落ちた回や、時間切れで止まった回は、Claude 自身は何も言えません。

そこで、報告は Claude にさせず、**起動したシェルの側から送る**形にしました。

```bash
# 実行スクリプトの最後（成功でも失敗でも通る場所）
trap 'python3 report_mail.py send --job "毎朝の見回り" --status "$STATUS" --log "$LOG"' EXIT
```

- 成功・失敗・打ち切りのどれでも1通届く
- 何もしなかった回も「区分: なし」で届く（届かないこと自体が異常の印になる）
- Claude には最後に「要旨・区分（新規／改善／変更／修正／なし）・内容」の囲みを書かせ、シェルがそれを件名と本文にする

10月30日から11月13日までの15日間で、送った報告は **229通**、多い日は1日28通でした。多すぎると読まなくなるので、売買の見張りのように5分おきに動くものは「何か起きたときだけ」送る、と分けています。

## 2. 見張り役が、動かなかったジョブを見つける

報告メールだけでは、**そもそも起動しなかったジョブ**に気づけません。届かないメールは目立たないからです。

そこで毎晩1回、別の見張り役のジョブが全部の登録を見て、次の4つを探します。

1. 読み込まれていない
2. 常駐のはずのものが落ちている
3. 予定の時刻から3時間たっても報告が届いていない
4. 止めたはずなのに読み込まれている

3つ目には落とし穴がありました。Mac が寝ていた時間のジョブも「届いていない」になり、毎晩それが並びます。そこで、予定の時刻の前後2分にシステムのログが1行も無い回は「Mac が止まっていた」と書き分け、異常に数えないようにしました。

止めたジョブは、設定ファイルに**理由つきで**書きます（今は12本）。理由を書かずに止めると、1か月後に「なぜ止めたのか」がだれにも分からなくなるためです。

## 3. 学びの台帳で、結果を次の判断に使う

記事のネタ選び、営業の送り先、作曲の指示文のように、**判断をする**定期実行は、測るだけでは良くなりませんでした。前回の結果を読まずに、毎回同じ判断をするからです。

そこで、判断をするジョブには次の4つを毎回させています。

1. 最初に、自分の台帳（`docs/learning.md`）の「学びの要約」を読む
2. 前回以降に出た結果（表示・クリック・返信・採否など）を確かめる
3. 結果が出た分だけ、1件1行で台帳に書く（日付｜何をしたか｜結果と出典｜次にどうするか）
4. 完了報告に `[学び] 使った: …／足した: …` の1行を入れる

台帳はプロジェクトに13、部署ごとに1つずつあります。週に1回、別のジョブが全部の要約を読み、ほかの部署にも効きそうな学びを共有の台帳にまとめます。

決めているのは、**学びから手順書を自動で書き換えない**ことです。直したほうがよいと分かっても、報告で「提案」として出し、人間が承認してから直します。自動で書き換えると、間違った学びが静かに積もっていくためです。

## 4. 守りのフックで、うっかりを止める

Claude Code の Hooks（ツールを使う前後に自分のスクリプトを挟む仕組み）で、3つの見張りを置いています。

| フック | 見るもの | 止め方 |
|---|---|---|
| 危ないコマンドの見張り（PreToolUse） | `rm -rf`・`git push --force`・`git reset --hard`・`sudo`・鍵のファイルの中身を画面に出す命令 | 実行の前に人間の確認に回す（勝手に書き換えない） |
| push の前の確かめ（git の pre-push） | 送るコミットに鍵の形の文字列や `.env` などが無いか（gitleaks・値は伏せて出す） | 見つかれば git が push を断る |
| 返事の言語（Stop） | 最後の返事が英語になっていないか | 書き直させる |

どれも「わざと抜ける手」まで塞ぐものではありません。目的はうっかりを止めることです。もう1つ決めているのは、**見張り自体が壊れたときは何もせず通す**ことです。見張りのバグで毎日の作業が全部止まるほうが、被害が大きいからです。

## 5. 部署は、ボトルネックが見えてから足す

前回の記事のあと、部署は「困りごとが見えてから定義を書く」という形で足し、いまは15あります。

| 部署 | 足したきっかけ |
|---|---|
| クイズテスター（監査） | 問題を作る側の自己点検は、作る側と同じ思い込みを持つ。作った道具・点検の結果を見ずに、自分で解き直す担当を分けた |
| コンプライアンス監査役 | ルール・メモリ・実装が食い違っていても、COO は自分で気づけない |
| 記事監査役・ソースハンター（調査） | 数百件の既存記事の確認や出典の裏取りで、メインの会話の容量が埋まる |
| SEO担当・マーケター | 毎週・毎朝の見回りで、同じ数字の取り方を毎回説明し直していた |
| SNS担当 | 投稿の前のアカウントの切り替えと戻しを、毎回手で確かめていた |
| セキュリティ担当 | 依存の脆弱性と鍵の混入の確かめが、週によって抜けた |

部署の定義には「やってよいこと」より先に、**やらないことと報告の形**を書きます。たとえばマーケターは読む・調べる道具だけを持ち、本番もファイルも変えられません。

## 実際に起きた失敗と、足した決まり

仕組みは、失敗のたびに1行ずつ増えています。最近の3つです。

**11月6日：長い URL をそのまま投稿した**
計測用の UTM を付けた長い URL を、SNS にそのまま出しました。決まりは別のプロジェクトのメモリにだけ書いてあり、その会話は読んでいませんでした。→ 決まりを全プロジェクト共通の rules に上げ、さらに「ほかのプロジェクトの仕事を頼まれたら、先にそのプロジェクトのメモリを読む」入口の表を作りました。

**11月9日：直したのに、また0件だった**
営業の定期実行が共有のドライブのファイルを読めず、送信が0件になりました。直したつもりが、確かめるファイルの一覧から1つ漏れていて、2回目も0件でした。→ 「直す前に、その処理が使うファイル・道具・つなぎ先を全部書き出す」を決まりにしました。

**11月12日：自分の2コミットを push したら、11コミット出ていった**
同じフォルダで別の会話が作って push していなかったコミットが、一緒に出ていきました。あとで中身を確かめて問題はありませんでしたが、確かめる前に送っていました。→ 「push の前に、送るコミットを全部出し、鍵・個人の情報・大きいファイルを確かめる」を手順にし、自動で push するリポジトリには pre-push のフックを入れました。

どれも、AI が賢くなれば消える種類の失敗ではありません。**複数の会話と定期実行が同じフォルダを触る**こと自体から生まれる失敗です。

## これから始めるなら、この順番

1. 定期実行を1本だけ作る（毎朝の見回りなど、読むだけのもの）
2. その1本に、シェルの側から送る完了報告を付ける
3. 2本目を作る前に、見張り役を作る
4. 判断をするジョブを作ったら、学びの台帳を付ける
5. 1回うっかりが起きたら、その操作を止めるフックを足す
6. 同じ説明を2回したら、部署の定義を書く

組織図からではなく、**報告と見張りから**作るのが、遠回りしたあとの結論です。
