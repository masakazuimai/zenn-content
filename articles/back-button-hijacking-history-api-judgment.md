広告や計測タグを載せたサイトの運用担当者と、ページ全体を読み直さずに画面を切り替える SPA（Single Page Application）の開発者に向けた記事です。結論から言うと、`pushState`（ブラウザの履歴に項目を追加するメソッド）が記録されたら、何をきっかけに履歴が増え、戻るとどこへ着いたかをセットで見ます。

## Google の方針が見るのはブラウザ内の戻り方

この二つを照らし合わせる理由は、Google がブラウザ内で利用者の戻る動作を妨げるページを対象にしているからです。リンク元に戻るつもりで操作した人が、見覚えのないページや頼んでいない広告に誘導される挙動が当てはまります。

Google Search Central は 2026-04-13 にこの行為を明示的な違反として扱う方針を発表し、2026-06-15 に施行しました。2026-11-23 に適用範囲を示す FAQ が加わりました。Google のスパムに関するポリシーでは「悪意のある行為」に当たり、手動による対策（Google が手動で行う措置）や、自動で順位を下げる処理の対象になり得ます。

FAQ の範囲には、第三者の広告コードが原因のページや、SNS のリンクをたどって入ったページも含まれます。Discover（Google 検索の一部）にも同じ方針が適用されます。ブラウザから外部アプリへ切り替わった後、そのアプリ内で戻れなくなる挙動は範囲外です。

## 履歴が増えたきっかけと、一回戻った先を照合する

ブラウザ内の妨害かを判断するには、戻る直前までに利用者が選んだ状態をたどります。履歴を操作する仕組みを History API と呼びます。この API の `replaceState` は現在の履歴項目を書き換え、`popstate` は履歴を移動したときに処理のきっかけとして使えるイベントです。

| 観察した処理 | 戻り先と照らしたときの読み方 |
| --- | --- |
| タブのクリックで `pushState` | 一回戻ってクリック前の表示を復元できるなら、利用者の選択と履歴が対応しています。 |
| 読み込み時に `pushState`、戻ったときの `popstate` で別ページへ移動 | リンク元に戻るつもりの操作で別ページが開きます。履歴を増やす箇所と、移動先を変える箇所を追います。 |
| スクロールで `pushState` | 読み進めただけで同じページの状態が履歴に積まれ、一回戻っても記事内に留まることがあります。 |
| `popstate` の処理を登録 | 登録元を手がかりに、履歴の追加や実際の戻り先も確認します。 |

タブの場合は、クリックして選んだ表示に対応する履歴があると、戻る操作で選択を取り消せます。スクロール位置を URL に反映するだけなら、現在の項目を更新する方法が使えます。どちらも URL が変わり得ますが、一回戻ると復元したい状態が違います。（MDN の History API）

## 同じ false から二つの戻り方を読み取る

二つの軸を使うと、開始 URL に戻れなかった試行でも、次に調べる処理を絞れます。2026年11月26日に Mac、Chrome 158.0.8127.37、Playwright 1.64.1、Node.js v23.10.0 で測りました。Playwright はブラウザ操作を自動化するツールです。各対象へ `start.html` のリンクから入り、戻った URL が開始 URL と一致したかを `backToStart` に出しました。

| 対象 | 戻る前の観察 | 履歴数 | 戻り先 | `backToStart` |
| --- | --- | ---: | --- | --- |
| plain | 記録なし | 3 | `start.html` | true |
| spa | ページ内のボタンを押さず3秒待機。履歴追加0件、登録1件 | 3 | `start.html` | true |
| bad | 読み込み時に履歴追加2件、登録1件 | 5 | `promo.html` | false |
| scroll | 3000pxスクロール。履歴追加3件 | 6 | `scroll.html?page=3` | false |
| cq | 記事を3000pxスクロールして10秒待機。履歴の追加・置換0件、登録2件 | 3 | `start.html` | true |

plain の 3 はこの計測での基準です。bad の追加と登録は同じ `ad-sim.js` に集中し、戻った先は `promo.html` でした。scroll は `?page=4` まで進み、一回戻ると同じページの `?page=3` でした。bad では別ページへの移動先を追い、scroll では読み進める途中で履歴を積む条件を追います。

呼び出し元は、元のメソッドを記録処理で包んで追えます。次は `history-watch.js` から `pushState` の部分だけを取り出し、記録する項目を減らして短くした形です（実際の記録では `replaceState` と `navigator.userActivation.isActive` も残しています）。`where()` は呼び出しの経路を文字列にする関数です。

```javascript
const original = history.pushState;
history.pushState = function (...args) {
  log.push({ type: 'pushState', url: String(args[2] ?? location.href), from: where() });
  return original.apply(this, args);
};
```

## 計測タグの登録は戻り先とセットで読む

履歴を実際に増やした記録と戻り先を対応づけると、登録の記録だけを原因と見なす誤りを避けられます。cq で `popstate` を登録したのは、計測タグの GA4 と Microsoft Clarity です。このとき履歴を追加・置換した記録はなく、開始ページに戻れました。

GA4 には履歴の変化を検知してページビューを送る設定があり、今回の登録はその検知に使われたと考えられます。`from` が示すのは登録を行った場所です。bad のように同じファイルが履歴も追加し、別ページへの移動も観察されたときは、そのファイルの処理に調査を進められます。

## Chrome の介入があっても戻り方を測る

タグの記録と同様に、ブラウザに履歴の乱用を抑える仕組みがある場合も、実際の戻り先を見ます。Chrome Platform Status には、ユーザー操作を伴わない履歴追加への介入が既定で有効だと記載されています。

bad の試行では、Playwright の `page.goBack()` と Chrome 拡張機能からの戻る操作の両方で、追加された履歴は飛ばされず `promo.html` が開きました。人が Chrome のツールバーの戻るボタンを押す試行は行っていません。利用者の報告と照らす場合は、どの方法で戻ったかも記録に添えます。

## うまくいかないときは測った条件を見直す

戻る操作の方法で観測範囲が決まるように、対象ページに入った後の操作でも確認できることが変わります。spa の true は、ページ内のボタンを押さずに戻れた結果です。タブの設計を見たいときは、タブを押してから一回戻り、クリック前の表示を確かめます。

`backToStart` が false でも、`afterBack` が期待したページなら URL の表記を確認します。この値は開始時に渡した URL と戻った URL の文字列比較です。cq のように広告も点検する場合、AdSense の読み込みは今回の自動操作では記録に出なかったため、判断できるのは記録が得られた条件までです。

## 修正する箇所は再現できた経路から選ぶ

測定条件を絞れたら、開始 URL、リンク、待機時間、スクロール量、戻り先を控え、履歴操作の `from` で修正箇所を探します。到着だけで履歴を足す自サイトの処理は取り除き、スクロール位置を URL に残すだけの処理なら `replaceState` に替えます。

広告やタグが原因なら、そのスクリプトを読み込む設定を確認し、原因の機能を止めます。設定で切り分けられないときは、対象 URL、呼び出し元、戻り先を提供元に伝えます。修正後は同じ経路と操作で戻れることを確認し、手動による対策を受けていた場合は Search Console の「手動による対策」から再審査をリクエストします。

## まとめ

修正後に同じ経路をたどると、履歴を変えた処理と戻り先がどう変わったかを比較できます。調査記録には API 名に加えて、履歴が増える直前の操作と一回戻った先を残します。これが、タブの状態復元と、利用者が来たページへの移動を妨げる挙動を見分ける材料になります。
