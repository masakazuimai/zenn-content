夜と朝に動かす作業が残っているのに、Claude の週の使用量はもう91%でした。記事を書くために資料を読み始める前に、どの工程なら手持ちの ChatGPT プランに含まれる Codex で進められるかを考えました。

Claude Code を日常的に使っていて、使用量の上限を意識しながら作業を組みたい中級者向けの記事です。記事制作を分担して見えてきたことは、次のとおりです。

- 資料を読む工程と下書きを Codex に渡し、記事に載せる内容の確認と公開の判断は Claude Code 側に置きました。
- 既存記事と照らす工程まで Codex に広げても、Claude 側の照合にかかった量は約2割の減少でした。
- 12月から対象プランで ChatGPT と Codex の使用枠が共有になるため、ChatGPT で普段どれくらい会話するかも分担を考える材料になります。

## 振り分け先を決める前に、どの枠を使うかを見る

この分担の出発点は、週末まで夜と朝の自動実行に使う分を残しておきたかったことです。記事を書き上げるまでの作業をまとめて考えると、資料の読み込みから公開まで、Claude の枠をどこで使うかが見えにくくなります。

Claude の Pro・Max には5時間ごとの上限と週の上限があり、Claude アプリと Claude Code がその枠を使います。サブエージェント（メインの会話から仕事を受け取り、独自の文脈で動く補助役）に資料読みを任せた場合も、消費先はメインの会話と同じ枠です。

サブエージェントを使えば仕事を切り出すことはできます。今回気になっていたのは、その仕事を終えたあとに Claude の枠がどれくらい残るかです。そこで、当時ほとんど使っていなかった Codex に、記事の準備を回すことにしました。

枠の扱いは Anthropic ヘルプ「Use Claude Code with your Pro, Max, or Ultra plan」と Claude Code ドキュメント「Create custom subagents」を参照しました。

## 下書きを渡すには、採用する材料を先に決める

Codex に記事の準備を回すと決めてから、考えたのはどんな状態で成果物を受け取りたいかです。調査では記事の裏付けに使えそうな情報が欲しく、下書きでは確認済みの材料を使って文章を組み立ててほしい。この違いを依頼文に反映しました。

調査では、一次ソースや検索候補を確認し、関連する検索語へ調べる範囲を広げる作業も頼みました。集まった情報のうち記事に載せる事実や数字は、Claude Code 側で出典と突き合わせます。その確認を済ませた一覧と、書式の見本になる記事の HTML が、下書きの入力です。

先に材料を絞っておけば、下書きを受け取ったときに、何を根拠に書いたかを一覧に戻って確認できます。初回は点検で事実の誤りは見つからず、書式も一度で通りました。筆者が Claude 側で手を入れたのは、題の長さです。

記事を出せる状態かどうかは、本文だけでは決まりません。既存記事と内容がかぶるか、書式や差分に問題がないかを確認し、画像の扱いや公開、公開後の記録まで Claude Code 側で扱いました。

## 照合を移しても、起動時に読む量が残った

下書きの確認が軽く済んだ初回でも、既存記事との照合は Claude 側に大きく残りました。サブエージェントは451本すべての本文を読み、約16万トークンを使いました。トークンとは、モデルがテキストを処理するときに使う単位です。

そこで次の記事では、何が似ているかを拾う作業と、その結果から記事として扱えるかを決める作業を分けました。Codex には既存452本の題・見出し・本文を渡し、似ている記事を表にしてもらいました。表に載った190本のうち、120本は題からは分からず、本文を検索して出てきた候補です。

Claude 側の補助役に残したのは、Google Search Console の検索の数字を見ることと、候補を踏まえて判定することです。本文を読む仕事は Codex に移しましたが、表示は約13.2万トークンで、前回からの減少はおよそ2割にとどまりました。

この回で使ったトークンの大半は、起動時に取り込む決まりとメモリ（作業に使う記録）に費やされていました。依頼する仕事を絞ることと、仕事に取りかかるまでに読み込む量を減らすことは、別々に考える必要がありました。

使用枠の表示も別に見ています。初回の記事制作で Claude の週の表示は91%から92%に進み、Codex は5時間枠の6%、週の枠の1%を使いました。それぞれの割合は異なる枠を基準にしているので、工程の重さを見直すときは、個別の出力に表示されたトークンも手がかりになります。

## うまくいかないとき・気をつけること

照合をどこまで回すかが決まったら、実行時に許す操作も依頼に合わせます。サンドボックスは、実行中のコマンドに許す操作の範囲を決める仕組みです。まずは Git リポジトリの中で、読むだけの依頼なら Bash から次のように呼べます。

```bash
codex exec -s read-only '既存記事の一覧を読み、内容が重なりそうな候補を挙げてください。'
```

ファイルとして下書きを受け取る場合は、書き込みを認める設定を選び、依頼文に出力先を書きます。公開や送信、鍵の読み取り、別の作業中のファイルへの操作は依頼の範囲から外します。受け取ったあとは、変更されたファイルと、その中身を確かめます。

Git リポジトリの外で起動時に止まったときは、作業場所が安全だと確かめたうえで `--skip-git-repo-check` を使えます。リポジトリ内では通常どおり呼び出せます。実行の仕組みは OpenAI「Non-interactive mode」を参照しました。

Codex の使用枠を使い切ったときは、Claude で作業を続けるか、Codex の枠が戻るまで待ちます。夜と朝の自動実行を予定しているなら、その分を Claude 側に取っておくかが判断の基準です。

## 12月からは普段の会話も分担を考える材料になる

枠が足りないときにどちらで続けるかは、Codex 側にどれだけ余裕があるかでも変わります。今回の分担を決めたときは、普段の ChatGPT の会話は Codex の枠に入らないと考えていました。

2026年11月22日に確認した OpenAI ヘルプ「Understanding ChatGPT and Codex usage limits」の案内では、12月から Plus・Pro・Business で ChatGPT と Codex が使用枠を共有します。使用量はトークンで数えられ、モデルや作業によって変わります。

資料を読んで候補を出す工程を渡し、採用や公開の判断を手元に置く、という分担は今後も考えられます。その日の残り枠を見て作業先を決めるなら、記事制作で動かす Codex と日常の ChatGPT の会話を合わせて考えることになります。

実際に渡した資料や、記事ごとの作業記録は元の記事に載せています。
